# Music Tag Auditor 仕様書

クラシック音楽ライブラリ向け タグ検査・編集デスクトップアプリケーション

策定日: 2026-08-02 / 版: 0.2（実装前）

---

## 1. 目的と背景

`TAGGING_POLICY.md` に定めた原則に沿って、音楽ライブラリのタグを検査・修正するツール。

現状これらは手作業（スクリプト＋表計算）で行っており、1,041ファイルの整理に対して調査・計画・適用・検証の各段階でスクリプトを書き起こす必要があった。本アプリはこの往復を GUI に置き換える。

**設計上の最重要方針**: 一括処理ツールでありながら、**適用前に必ず差分を人間が確認できる**こと。原則で確信が持てない項目を自動で埋めないこと。これは実作業で「誤った値で埋めるより空欄のほうが後から対処できる」という判断に至ったことによる。

---

## 2. スコープ

### 2.1 対象とする

- ライブラリ全体の走査と原則違反の検出
- 検出結果の一覧表示、絞り込み、差分プレビュー
- 一括適用（選択したものだけ適用できる）
- 個別ファイル／アルバム単位の手編集
- 正規化辞書の閲覧・編集
- タグのバックアップと復元

### 2.2 対象としない（v1）

- 音声の再生
- ファイル名・フォルダ名のリネーム（`TAGGING_POLICY.md` 6.7。v2 で検討）
- カバーアート編集
- オンライン楽曲DB（MusicBrainz 等）との照合
- タグ以外のメタデータ（ReplayGain 等）の書き換え

## 4. タグ入出力ライブラリの選定（未決・要検証）

**この判断を実装開始前に済ませること。** アプリの根幹に関わる。

候補は TagLib# (TagLibSharp) と ATL.NET。TagLib# が事実上の標準だが、本ライブラリの要件には確認が必要な点がある。

### 4.1 検証項目

| # | 確認すること | なぜ重要か |
|---|---|---|
| V1 | **M4A の Conductor をどの atom に読み書きするか** | AIMP は `©con` を使う（検証済み）。ライブラリが別の atom（`cond` 等）を使うと AIMP から見えなくなる |
| V2 | 未知の4文字 atom を直接読み書きできるか | V1 が不一致だった場合、`©con` を直接扱う必要がある |
| V3 | 既存のフリーフォーム atom（`----:com.apple.iTunes:*`）を保存時に破壊しないか | iTunNORM 等が消えると音量正規化情報が失われる |
| V4 | カバーアート（`covr`）を保存時に保持するか | |
| V5 | FLAC の `CONDUCTOR`、ID3v2 の `TPE3` を扱えるか | こちらは規格内なので問題ない見込み |
| V6 | AIFF の ID3 チャンクを読み書きできるか | 本ライブラリに11ファイル存在 |
| V7 | 保存時に `;` を複数値に分割しないか | AIMP はこの挙動を持つ。アプリ側は分割しない方が制御しやすい |
| V8 | **.NET 10 に対応しているか** | TagLib# は更新が停滞気味との指摘がある。`net10.0` で動作するか、最終更新はいつかを確認する |

### 4.2 検証方法

`TAGGING_POLICY.md` 4.3 と同じ手順を .NET 側で再現する。テスト用にコピーしたファイルへ書き込み、(a) ライブラリ自身で読み戻す (b) AIMP で開く (c) バイナリレベルで atom を確認する、の3方向から突き合わせる。

V1 が不一致だった場合の対処案:

- 案A: `©con` への低レベルアクセスを持つライブラリに切り替える
- 案B: MP4 atom の読み書きだけ自前実装する（`moov/udta/meta/ilst` 内の単純な構造）
- 案C: TagLib# を使いつつ `©con` のみ後処理で書き込む

### 5.2 タブ

**検査結果タブ** — 上段に検出ルール別の集計（チェックボックス付き）、下段に選択したルールの差分明細。明細行も個別にチェックを外せる。上段・下段それぞれに「全選択」「全選択解除」「選択反転」を持つ。上段の操作は全ルール配下の明細に効き、下段の操作は選択中ルールの明細だけに効く。

左ツリーで選んだフォルダ配下だけに絞り込めること。**絞り込みは既定 OFF のチェックボックスで明示的に切り替える**（5.3）。作曲家フォルダ単位で少しずつ直していく作業を、全体の検出件数に埋もれさせないため。

**ファイル一覧タブ** — 全ファイルの現在のタグを表形式で表示。列の並べ替え・絞り込み・セル直接編集に対応する。手編集はここで行う。複数行を選択して同一値を一括入力できること（アルバム単位の編集で必須）。**選択には「全選択」ボタンを置く**。`Ctrl+A` は一覧にフォーカスが無いと効かず、絞り込みや値の欄で手を止めたままフォルダをまたいだ修正に移れない。選択の対象は絞り込みで残っている行だけ。

`composer` / `artist` / `conductor` / `albumartist` のセル編集と一括入力の欄では、**辞書由来の候補を絞り込みながら出す**。辞書は正規形を持っているのに、手打ちだと表記が揺れて次の検査で跳ね返る（辞書に無い値は自動修正の対象にもならない）。

- 照合は辞書引きと同じ正規化キーで行い、**別名・日本語表記でも一致させる**。確定して入るのは**正規形**。別名や日本語表記をそのまま入れられると、原則に反する値を候補から選べてしまう
- **候補は入力を助けるだけで、入力を縛らない。** 辞書に無い名前も自由に入る。原則の例外や、これから辞書に足す値を先に入れることがある
- 辞書が扱わないフィールド（曲名・アルバム・ジャンル・年・トラック・ディスク・コメント）では候補を出さない

`comment` は版・稿の注記を置く欄で（`TAGGING_POLICY.md` 2.4）、**ID3（`.mp3` / `.aif`）では扱わない**（同 4.4）。扱えない組み合わせを編集したときは手編集の気づきで理由を出す。**行ごとに編集可否を変える作りにはしない。** 対象は実測 15 ファイルで、そのために一覧の編集経路へ 2 本目の分岐を持ち込むと、編集確定と絞り込みの掛け直しという既存の繊細な作りを壊す危険のほうが大きい。

**`comment` は「空欄のある行のみ」の絞り込みでは見ない。** 必要なファイルにしか入らない欄なので、含めるとほぼ全行が該当し、`composer` / `conductor` の欠けを探すというこの絞り込みの目的が果たせなくなる。検索の対象には含める（入れた注記を後から辿れないと、一括入力の前段になる絞り込みが成立しない）。

フォルダ欄は相対パスのフォルダ部分を出すため、**ライブラリルート直下のファイルでは空になる。** 空欄のままだと「ルート直下」なのか「値を取り損ねた」のか読み取れないので `(root)` と表示する。表示だけの置き換えで、絞り込みと並べ替えは元の値で行う。

**行を右クリックするとエクスプローラーでそのファイルを表示できる。** 一覧で見つけたファイルを実物のフォルダで確認したいとき、パスを目で読んで開き直す作業が要らなくなる。ファイルが選択された状態で開く。

**一覧を CSV に書き出せる。** 絞り込んだ結果を表計算ソフトで確認したり、手を入れる前の状態を記録として残したりするための出口。

- **書き出すのは画面に出ている行だけ。** フォルダの絞り込みも検索も効いた結果をそのまま出す。検査結果の CSV 出力と同じ理由で、表と CSV で件数が違うとどちらが本当か確かめられない（5.3）
- **値は保留中の手編集を反映する。** セルに見えているとおりを書く。まだファイルには書き込んでいない状態なので、編集した行には印を付けて区別できるようにする
- 複数値として格納されている行にも印を付ける。CSV では値が連結されて 1 つに見え、画面のような行の色分けが使えない（`TAGGING_POLICY.md` 3.4）
- 集計ファイルは出さない。検査結果と違い、ルールのような集計の軸が無い

**辞書タブ** — 正規化辞書の閲覧・編集（7章）。

### 5.3 差分プレビューの要件

- 変更前 / 変更後 を横並びで表示し、変更箇所を色分けする
- 「根拠」列を必ず持つ（例: `フォルダ名「ブルックナー 8 - ショルティ」から特定`）。自動判定の理由が読めないと承認できない
- **根拠列は読める幅を確保する。** 列幅をウィンドウ幅で全列按分すると根拠列が真っ先に潰れるため、根拠以外の列に実幅を与え、余った幅は根拠列だけが取る（下限幅を割ったら横スクロールで見せる）。行の折り返しはしない（仮想化スクロールの体感を落とさないため、行高は固定のまま）
- **それでも入り切らない根拠は、ツールチップで全文が読めること。** ツールチップは折り返す。折り返さないと 1 行のまま最大幅の外へ伸び、ポップアップごと切り落とされて結局読めない
- 差分プレビューを持つ画面（検査結果タブ・ファイル一覧タブの手編集差分）は同じ幅体系にそろえる
- 判定区分（確定 / 要確認 / 保留）で色を変える
- **適用チェックの変更は即座に反映する。** 明細行のチェックを付け外ししたら、その場で選択件数の表示と「チェックした項目を適用」の活性が変わること。既定で 0 件選択の検査結果でも、利用者が明細をチェックすれば適用に進める（検査をやり直さないと進めない、という状態を作らない）
- **ルール行のチェックは、表示中の明細のチェックへ即座に反映する。** ルールを選び直すまで下段が古い表示のまま、という状態を作らない
- **上段・下段それぞれに「全選択」「全選択解除」「選択反転」を持つ。** 「選択反転」は行単位の一括トグルではなく、明細（ファイル・フィールドの組）ごとに個別にチェック状態を反転する
- **ルール行のチェックは、配下の明細が変わったら追従する。** 配下だけが変わってヘッダーが取り残されると、画面が実態と食い違い「操作しても何も起きない」ように見える。混在は `bool` で表せないので、配下が全件チェック済みのときだけチェック状態にする。**このときヘッダーから配下へ撃ち返さないこと。** 「明細を 1 件外した」が「そのルールを全件外す」に化ける
- **修正案を持たない明細は、そもそもチェックできないようにする。** 適用時は `IsSelected` かつ修正値を持つものだけが書き込まれる（9章）。チェックだけできて適用されない状態を許すと、「選択 N 件」の表示と実際の適用件数が食い違う。チェックボックスを無効表示にし、一括操作の対象からも外す。対象が 1 件も無いルールでは、一括操作のボタン自体を押せなくする（押しても何も起きないボタンを残さない）
- **明細行のダブルクリックで、ファイル一覧タブの当該行へ移動できる。** 修正案を出せなかった行は手で直すことになるが、タブを切り替えてツリーを辿り、パスを打ち込んで目で探すのでは明細を 1 行ずつ潰していけない
  - ツリーは対象ファイルのフォルダを展開して選択し直す。ツリーの表示と一覧の中身が食い違わないようにするため
  - ファイル一覧の絞り込みは、**対象行を隠しているものだけ**を解除し、解除した項目をステータスバーに出す。利用者が組み立てた絞り込みを毎回捨てると、明細を順に確認していく作業のほうが壊れる。黙って解除もしない
  - 対象は差分明細（下段）だけ。上段はルール単位の集計でファイルに対応しない
- **左ツリーで選んだフォルダ配下だけに絞り込めること。** 作曲家フォルダ単位で潰していく作業では、全体の検出件数に埋もれると対象が見つけられない
  - **絞り込みは既定で無効にする。** ツリーはファイル一覧タブの操作にも使うため、フォルダを選んだだけで検査結果が黙って狭まると、全体を見ているつもりの利用者を欺く
  - **絞り込みの範囲は、表示だけでなく一括選択・適用・CSV 出力にも一致させる。** 画面に出ていない項目が書き込まれる状態を作らない。上段の件数（検出 / 修正可 / 保留）も同じ範囲で数え、配下に検出が無いルール行は表に出さない
  - **範囲外になった項目のチェック状態は書き換えない。** 絞り込みを外したら元の選択がそのまま戻ること。適用対象の唯一の真実は変えず、どこまでを対象として見せるかだけを変える
  - 絞り込み中は、要約テキストと適用の確認ダイアログに**対象フォルダを明示する**。件数だけ減っていると、検査し直したのか絞ったのかが読めない
  - ツリーのルートを選んでいるときは絞り込まない。ファイル一覧タブの絞り込みと基準を揃える
- **差分プレビューをチェック済みの行だけに絞れること。** 検出が数百件あるルールでは、これから書き込む内容を最後に見直す手段が要る
  - **これは表示だけの絞り込みにする。** 隠すのは適用されない行だけなので、件数・一括選択・適用・CSV 出力はどれも動かさない。フォルダの絞り込みが対象範囲そのものを狭めるのとは性質が違う。絞っているあいだは「選択 N 件」と画面に出ている行数が一致する
  - **既定は無効。** 検査直後は既定のチェックを見直すところから始まるので、未チェックの行が最初から隠れていては選びようがない
  - 絞り込み中にチェックを外した行はその場で一覧から消える。**明細そのものは残す。** 絞り込みを外せば元のチェック状態のまま戻る

### 5.4 起動時のライブラリ復元

最後に開いたライブラリを設定（`%APPDATA%\MusicTagAuditor\settings.json` の `lastLibraryRoot`）に記録し、次回の起動時に自動で開いてスキャンする。**同じライブラリを繰り返し扱う道具なので、毎回フォルダを選び直させない。**

- 第 1 引数にライブラリのパスが渡された場合はそちらを優先する。引数はその場の明示的な指示で、記憶しているパスは前回の名残にすぎない
- 引数のパスが存在しない場合は、記憶しているライブラリで代替せずに何も開かない。指定したものと違うライブラリが開くと、どちらを見ているのか分からなくなる
- 記憶しているライブラリが見つからない場合は、その旨をステータスバーに出すだけで**設定からは消さない**。外付けドライブを外しているだけかもしれず、一度きりの不在で忘れると次に繋いだときに選び直しになる
- 記憶するのはライブラリのパスだけ。スキャン結果・検査結果・保留中の手編集は持ち越さない

## 6. 検査ルール

ルールは ID・重大度・説明・自動修正可否を持つ。重大度は 3 段階。

- ⛔ **error** — 原則違反が明確で、修正値も一意に決まる
- ⚠ **warning** — 原則違反だが、修正値の決定に文脈が要る
- ❓ **info** — 人間の確認が必要。自動修正しない

**画面では記号ではなく文字で示す**（`エラー` / `警告` / `要確認`、手編集は `手編集`）。記号は実描画で単色の代替字形に置き換わり、塗りと線の違いしか出ないため意味が読めない。文字に色を添えて区別する。本書で記号を使っているのは表記の都合であり、画面の表示ではない。

### 6.1 ルール一覧（初版）

| ID | 重大度 | 内容 | 自動修正 |
|---|---|---|---|
| R-101 | ⚠ | `genre` が `Classic` 以外 | ○ |
| R-102 | ⚠ | `genre` 未設定 | ○ |
| R-103 | ⚠ | `discnumber` 未設定 | △ 単一ディスクなら `1/1` |
| R-104 | ⚠ | `date` が4桁でない | ○ ISO形式から年を抽出 |
| R-105 | ❓ | `date` 未設定 | × |
| R-201 | ⛔ | `composer` が辞書の正規形と不一致 | ○ |
| R-202 | ⛔ | `artist` / `conductor` / `albumartist` が辞書の正規形と不一致 | ○ |
| R-203 | ⛔ | `artist` に作曲家名が入っている | △ 指揮者を特定できた場合のみ |
| R-204 | ⛔ | `albumartist` に作曲家名が入っている | △ 同上 |
| R-205 | ⛔ | 値に `;` が含まれる（AIMP が分割する） | △ |
| R-206 | ⛔ | 同一値の重複連結（`Anton Bruckner; Anton Bruckner`） | ○ |
| R-207 | ⚠ | 人名に生没年・「姓, 名」順・全大文字が含まれる | ○ |
| R-208 | ⚠ | 日本語表記の人名・団体名 | △ 辞書にあれば |
| R-209 | ⛔ | `albumartist` が収録時点の団体名と不一致（実体IDで判定） | △ `date` が空欄で決められない場合は保留（`HOLD_ERA_UNKNOWN`） |
| R-210 | ❓ | ファイル名・`title`・フォルダ名に `composer` と違う作曲家名が出てくる | × 判断を促すだけ（6.2 参照） |
| R-301 | ⛔ | 楽語・人名の typo（辞書の正規表現に一致） | ○ |
| R-302 | ⛔ | `title` に拡張子が含まれる（`....flac`） | ○ |
| R-303 | ⛔ | `title` がプレースホルダ（`Track04`、`ショス15 - 01` 等） | △ ファイル名から補完 |
| R-304 | ❓ | 曲名中のウムラウト欠落 | × 6.3 参照 |
| R-401 | ⛔ | `composer` 未設定 | △ 同一フォルダ内の他ファイルから推定 |
| R-402 | ⛔ | `conductor` 未設定 | △ 指揮者を特定できた場合のみ。特定できなければ ❓ に落とす（6.2 と同じ考え方） |
| R-403 | ⛔ | 文字化け（Shift-JIS の誤解釈を検出） | × 再入力が必要 |
| R-501 | ⚠ | 同一アルバム名に複数の作曲家／演奏者が混在 | × 同上 |
| R-502 | ❓ | アルバム名が日本語（略称・正式名とも） | × 書式は `TAGGING_POLICY.md` 3.5 で確定したが、`{作品名}` の供給元（作品エントリ / D6）が未整備 |
| R-503 | ❓ | 楽章番号の書式がフォルダ内で不統一 | × |
| R-504 | ⚠ | `album` が 3.5 の書式（`{作曲家}: {作品名} - {date}/{artist}`）と不一致 | △ 作品エントリ（7.4）で作品名が決まり、`date` と `artist` が単位内で一意な場合のみ。決められない場合は保留（`HOLD_WORK_UNKNOWN` / `HOLD_DATE_UNKNOWN` / `HOLD_ARTIST_UNKNOWN`） |

### 6.2 実装上の注意

- **文字列照合は正規表現で行う。** 完全一致辞書だと `Finale- Allgro molto` と `Finale: Allgro molto` の区切り文字違いを取りこぼす（実作業で10件の見落としが発生した）
- R-203 / R-204 の「作曲家名が入っている」判定は、辞書の作曲家名リストとの照合で行う
- R-203 の指揮者特定は次の順に試みる。いずれも失敗したら ❓ に落とす
  1. フォルダ名に含まれる指揮者名（辞書の日本語↔英語対応を使う）
  2. `albumartist` に含まれる指揮者名
  3. 同一アルバムの他ファイル
- R-304 は既定で無効。有効化すると誤検出が増えるため、ユーザーが明示的に選ぶ
- **R-210 は判断を促すためだけのルールで、修正案を出さない。** `composer` が「辞書の正規形として正しいが、そのファイルの作曲家ではない」状態は、値が辞書と一致してしまうため R-201 でも R-501 でも検出できない。ファイル名・`title`・フォルダ名に出てくる作曲家名だけが手掛かりになる（`TAGGING_POLICY.md` 6.9）
  - **曲名が別の作曲家の名前を正当に含む作品があるため、一致しても誤りとは限らない。** 例: ブラームス『ハイドンの主題による変奏曲』（`Variation über ein Thema von Joseph Haydn`）は `composer` が `Johannes Brahms` で正しく、曲名の `Haydn` は作品名の一部である。**この判別は機械ではできない**ので ❓ とし、自動修正も既定チェックもしない
  - **誤検出は辞書が育つほど増える。** 上の例は 2026-08-11 時点ではハイドンが辞書（`TAGGING_POLICY.md` 5.1）に無いため検出されない。ハイドンの録音を所蔵して辞書に足した時点で誤検出に変わる。実測の 3 件 / 0 誤検出という数字は、現在の辞書に対しての値にすぎない
  - 照合はファイル名と `title` の両方に対して語単位で行う。部分一致にすると `Bach` が `Bachmann` に当たる
  - **語に割る前に、値そのものが辞書の団体名・人物名かを見て外す。** `Münchener Bach-Chor` は語に割ると `Bach` が出てくるため、語単位にしただけでは防げない（`DictionaryIndex.ContainsComposerName` が値全体に対して行っているのと同じ判定）
  - **`composer` が未設定のファイルは対象にしない。** 本ルールは「値が辞書の正規形と一致するのに誤り」を扱う。未設定は R-401 の担当で、両方から出すと同じファイルが二重に明細へ出る
  - **フォルダ名は、フォルダ内の `composer` が 1 種類のときだけ手掛かりにする。** カップリング盤（`TAGGING_POLICY.md` 3.5 規則5）はフォルダ名が主作品の作曲家を名乗るので、併録曲が「フォルダ名と違う作曲家」になるのは正しい。この除外をしないと該当 4 単位が丸ごと誤検出になる。実測ではフォルダ名を加えて 3 件 → 7 件になり、増えた 4 件はすべて真の誤りだった（ファイル名にも `title` にも作曲家名が出てこないフォルダ）
- **R-504 はアルバム単位で判定し、単位内の全ファイルへ同じ値を出す。** 単位は「フォルダ + `discnumber`」（`TAGGING_POLICY.md` 3.5 補足2）。1 アルバムが複数ディスク・複数フォルダに分かれている場合も同じアルバム名にする（3.5 規則3）ため、ファイル単位で判定してはならない
  - 作品の同定手順・保留の種類・個別例外は 7.4 を参照
  - **R-501 / R-502 は R-504 に置き換わらない。** R-501（複数作曲家の混在）は 3.5 規則5・規則6 の対象を人が仕分けるための一覧であり、R-502（日本語のアルバム名）は R-504 が直せない単位を見つける手掛かりとして残る

### 7.3 辞書編集 UI

- 種別（composers / conductors / ensembles / typos / works / albumOverrides）ごとのタブ
- 正規形とエイリアスの追加・編集・削除
- **検査結果から直接追加できること。** 未知の値を見つけたとき、その場で「これは `Yevgeny Mravinsky` のエイリアス」と登録して再スキャンできる導線が最も使用頻度が高い（7.3.2）
- typos は正規表現の入力欄と、その場で試せるテスト欄を持つ
- 保存時に正規表現の妥当性を検証し、不正ならエラーを出す
- **辞書の構成（種別ごとの件数）を画面から読めること。** どの辞書を読んでいるかが分からないと、検出結果が想定と違うときに「ルールの誤り」なのか「別の辞書を読んでいる」のかを切り分けられない。同じ内容をログにも出す（`DictionarySummary`）
- **辞書ファイルをエクスプローラーで開けること。** パスを画面に出しているだけでは、控えを取る・別のツールで開くといった作業のたびに目で読んで打ち直すことになる。ファイル一覧タブの「エクスプローラーで表示」（5.2）と同じく、ファイルが選択された状態で開く
- **一覧は名前の昇順で表示する。** ファイルの配列順のまま出すと、育てるほど末尾が無秩序になり、同じ人物が 2 エントリに分かれていないかを目で確かめられない。ただし**並べるのは表示だけで、保存する順序は変えない**。`typos` は書かれた順に置換を重ねるため、表示の都合で並べ替えたものを保存すると置換の結果が変わりうる。JSON の差分も無用に膨らむ
- **番号は数として並べる**（自然順）。素の文字列比較では `Symphony No. 10` が `No. 4` より前に来る。作品名は番号で呼ぶものが大半なので、それでは一覧を目で追えない。数字以外の部分は現在のカルチャで比べる。序数比較にすると `Günter` のようなアクセント付きの名前が末尾に飛び、重複を見つけるという目的に合わない
- 並べ替えは読み込みと行の増減で効かせる。**編集中に行を動かさない**（ライブ整列は入れない）。打っている途中で行が跳ねると、どの行を編集していたのか見失う
- **検証結果の表示は閉じられること。** 承知のうえで残す警告（時代分割の隙間など、誤りとは限らないもの）が居座ると、編集領域の高さを取り続ける。消えるのは表示だけで、保存と「検証だけ実行」のたびに出し直される
- **索引に載らない別名をまとめて取り除けること**（「冗長な別名を掃除」）。正規化キーが重なる別名は先に書いたほうしか索引に載らず、残りは書いても引かれないまま検証の警告になる。既定辞書側を直しても**利用者辞書には届かない**（取り込みは追加しか作らない）ため、辞書自身で完結する導線が要る
  - **取り除く前に一覧を見せる。** 引ける範囲は変わらないが、辞書は利用者が育てたものであり、黙って中身を削ってよい理由にはならない
  - **1 件ずつ選ばせない。** 取り込みが行ごとにチェックを持つのは、利用者が意図的に消したエントリを復活させうるからである。こちらは消す別名がいずれも索引に既に捨てられているもので、残す理由が無い。意味の無い選択肢は「外すべき行があるのでは」と読ませる
  - **正規形と時代分割の正規形は決して落とさない。** これらは別名ではなく、消せば引けなくなる
- **検証結果の行から、その対象のエントリへ移動できること。** 問題を出すだけでは直せない。種別タブを選び直して一覧を目で辿る作業が挟まると、作品のように 100 件規模で並ぶ一覧では警告を潰していけない
  - 突き合わせは**一覧の見出しと同じ文字列**で行う。したがって検証は、一覧の見出しと同じ形で対象を名指しすること（作品なら `作曲家: 作品名`）。**この対応が崩れると移動が黙って効かなくなる**
  - 絞り込みは**対象を隠しているときだけ**外し、外したことを画面に出す。組み立てた絞り込みを毎回捨てると、警告を 1 件ずつ潰していく作業のほうが壊れる（5.3 のファイル一覧への導線と同じ扱い）
  - 対象が見つからないときは理由を出す。検証のあとに名前を書き換えると起きる
  - 選んだ行は一覧の見える位置まで送る。**WPF の一覧は選択を外から変えてもスクロールしない。** 選択だけ変わって画面が動かないと、操作が無かったように見える

#### 7.3.1 works / albumOverrides のタブ

| タブ | 列 | 備考 |
|---|---|---|
| works | 作曲家 / 作品名 / 別名 / 日本語別名 | 作曲家は**辞書の作曲家から選ぶ**（自由入力させない）。空のままにできない（7.4.3 の同定キーの一部） |
| albumOverrides | フォルダ / disc / 作曲家 / 作品名 / 対象外 / 理由 | **フォルダは基本的に手打ちさせない**（7.3.2）。編集・削除はできる |

- 一覧は他のタブと同じく絞り込めること。作品は 100 件規模になる
- `disc` は空欄をそのフォルダの全ディスクとして扱う（7.4.5）
- **`対象外` でも `作品名` でもない項目は保存できるが警告を出す。** 何も起きない例外になるため
- **`理由`（`note`）が空なら警告を出す。** 理由の書いていない例外は、後から消してよいか判断できない

#### 7.3.2 検査結果からの導線

**この 2 つが作品エントリを育てる主経路になる。** 辞書タブでフォルダの相対パスや作曲家名を手で打たせる作りにしない。打ち間違えれば黙って効かないだけで、原因が画面から分からない。

**作品を辞書に追加**（R-504 の `HOLD_WORK_UNKNOWN` の明細から）

- 作曲家はその単位の `composer` を**固定で表示する**（変更させない）。単位から決まっているものを選び直させる意味がない
- 別名の候補として、その単位の `album` の値とフォルダ名（7.4.3 と同じく「最初の `-` より前」も）を**初期値として入れておく**。人はそれを取捨選択する
- **作品名（`canonical`）は空で出し、人が入れる。** 現在の `album` の値は誤っていることがあり、機械が正規形として採用してはならない（`TAGGING_POLICY.md` 3.5 補足2）
- **作品名の候補は出す。押したときだけ入力欄に入る**（2026-08-12 追加）。`Nielsen Symphony No.4` を見ながら `Symphony No. 4` を毎回手で打たせない。**既定値にはしない**ので上の原則は保たれる。候補は次の 3 通りで作り、**それぞれ出所を添える**
  - 手がかりから**作曲家名を外して書式を整えた**もの（`Nielsen Symphony No.4` → `Symphony No. 4`）。**日本語を含む手がかりからは作らない。** 作品名は英語か原語で書く（3.5 規則8）ため作れず、残るラテン文字は演奏者であることが多い（`ブルックナー 8 - Wand` の `Wand`）
  - **同じ作曲家に既にある作品名**のうち、手がかりの番号と一致するもの。別名だけが足りていない場合はこれを選ぶのが正しい（新しい行は作らず別名が足される）
  - **辞書にある作品名の書式に番号を差し替えた**もの（`Symphony No. 8` + 手がかりの 4 → `Symphony No. 4`）。作品名の語彙は作曲家をまたいで繰り返すため、人が書いた正規形だけを素材にできる。**録音年を番号として扱わない**（フォルダ名に年が入る。`- ムラヴィンスキー 1982`）
- **`album` とフォルダ名が別の番号を指しているなら名指しで警告する**（7.4.3 手順5）。候補を並べるだけではこの食い違いは見落とされる
- **単位内に作曲家が複数ある場合は、この導線を出さない。** 作品を足しても保留は解けない。代わりに下の「このアルバムの扱いを決める」へ誘導する（3.5 規則5・規則6）

**このアルバムの扱いを決める**（R-504 の `HOLD_WORK_UNKNOWN`・年が割れている `HOLD_DATE_UNKNOWN`・R-501 の明細から）

- フォルダと `disc` は明細から**自動で埋める**
- **理由の入力を求める。** 空のまま登録させない
- 同じダイアログで「対象外にする」と「作曲家・作品名・年を指定する」を選べること。版の違い（3.5 規則4）や同一演奏の別リリース（規則7）は、対象外ではなく作品名の上書きで扱う
- **導線の名前を二択の片方にしない**（2026-08-15 改称）。「このアルバムを対象外にする」と名乗っていたため、R-504 が「主作品が定まるなら作曲家を指定する」（3.5 規則5）と言っていても、その入口がこのボタンだと気付けなかった
- **`HOLD_ARTIST_UNKNOWN` では出さない**（2026-08-15 追加）。個別例外に `artist` は無いので**書いても解けない**のに、対象外にすれば一覧からは消える。タグが割れたまま検出だけ消えた単位ができるので、押せる行から外す。`date` が未設定（値が 1 つも無い）の保留も同じ理由で出さない。**選べるのは単位内にある年だけ**なので、開いても選ぶものが無い
- **年の保留から開いたときは「対象外にする」を選ばせない**（2026-08-15 追加）。そこまで来た単位は作品が決まっている＝主作品が定まっているので、規則6 には当たらない。選べるままだと、規則2 の保留を規則6 で握り潰す操作が残る
- 押せない理由はツールチップに書く（`ToolTipService.ShowOnDisabled`）。無効なボタンは既定でツールチップを出さないため、そのままでは行き止まりに見える
- 登録して再検査すると、その単位は検査結果から**消える**（7.4.3 手順1）。消えたことが利用者に分かるよう、状態表示に反映する

いずれも既存の「辞書に無い値」→「辞書に追加」と同じ形（その場で登録して再検査できる）にそろえる。

### 7.4 作品エントリ（`works`）

`TAGGING_POLICY.md` 3.5 の `{作品名}` の唯一の供給元。**これが無いとアルバム名は 1 枚も組み立てられない。**
`{作品名}` は作品そのものの名前であり、`title`（楽章名）からも `album`（`Symphony No.5` のような汎用名）からも一意には取れないため。

#### 7.4.1 項目

| 項目 | 内容 |
|---|---|
| `composer` | この作品の作曲家。**`composers` の正規形と一致すること。** 引くときのキーの一部になる |
| `canonical` | 作品名。アルバム名にそのまま入る値 |
| `aliases` | ラテン文字の別表記。現在の `album` タグの値・フォルダ名のうちラテン文字のものを入れる |
| `aliasesJa` | 日本語表記。日本語略称（`ベト7`）と正式な日本語名（`交響曲第8番`）の両方 |

**自然キーは `composer` + `canonical` の組。** 別途 ID は持たない。`ensembles` の `entityId` は改名（時代分割）をまたいで同一性を保つために要るが、作品名は改名しないため同じ仕掛けは不要で、220 件分の ID を人が考える手間だけが増える。

**1 作品 1 エントリとする。版で分けない**（3.5 規則4）。ハース版／ノヴァーク版のような版・稿の情報は `comment` に置く。版だけが違う録音を所蔵した場合は、そのアルバムだけ `albumOverrides` で例外にする。

`comment` はファイル一覧タブで編集する（5.2）。アルバム単位で同じ値が入るものなので、複数行を選んでの一括入力が主な手段になる。**ID3（`.mp3` / `.aif`）では扱わない**（`TAGGING_POLICY.md` 4.4）。

#### 7.4.2 作品名の言語（2026-08-11 決定）

規則は `TAGGING_POLICY.md` 3.5 規則8 にある。**ジャンル名は英語、固有の題名は原語。ただし原語が非ラテン文字なら英語圏での一般的な題名を用いる。**

- `Symphony No. 8` / `Piano Concerto No. 5` / `String Quartet No. 14`
- `Die Walküre` / `Der Freischütz` / `Parsifal` / `Má vlast`
- `The Nutcracker` / `Swan Lake`（原語がロシア語のもの。ラテン転写は用いない。理由は Android Auto の頭文字検索）

3.5 の例示（ブルックナーを `Symphony No. 8` と書いている）がすでにこの形であり、書式の確定時の判断と揃う。**発音区別符号は 3.3 に従って正しく付ける。** 6.3（曲名中のウムラウト欠落）は既存タグの `title` をどう扱うかの話であり、作品エントリは人が新しく書くので迷いは生じない。

#### 7.4.3 アルバム単位から作品を同定する

**アルバム単位 = フォルダ + `discnumber`**（3.5 補足2）。次の順で決める。

1. `albumOverrides` に一致する項目があれば、それを最優先する（7.4.5）
2. 単位内の `composer` を正規形へ寄せて集める。**1 つに定まらなければ保留**（`HOLD_WORK_UNKNOWN`）。3.5 規則5・規則6 の対象で、機械では主作品を決められない
3. その作曲家に属する作品エントリだけを候補にする。**エイリアス単独では引かない。** `Symphony No.5` は作曲家が違えば別の作品であり、作曲家で絞らないと R-501 が検出している衝突をそのまま再生産する
4. 次の手がかりから引く。照合キーは他の辞書引きと同じ `NormalizationKey`
   - `album` タグの値（単位内で一意のもの）
   - 相対パスのフォルダ名。**末端のセグメントから順に親へ遡って試す。** `ワーグナー\ワルキューレ\第二幕` のように、作品名が親フォルダにしか出てこない構成があるため（3.5 規則3 の B 種別）
   - フォルダ名は**セグメント全体と、最初の `-` より前の部分**の 2 通りで引く。フォルダ名には演奏者が付いていることが多く（`ブルックナー 8 - Wand`）、全体でしか引かないと同じ作品が演奏者の数だけ別のエイリアスになる。ブルックナー 8 番だけで 7 単位ある
5. 両方が引けて**食い違ったら保留**。片方だけ引けたらそれを採る。どちらも引けなければ保留

**`album` タグだけを手がかりにしない。** 3.5 補足2 が名指しで警告している。実ライブラリには `シューベルト 9 - バーンスタイン` の `album` が `Schubert Symphony No.8` になっている例があり、`album` を信じると 8 番の作品エントリに吸い込まれる。フォルダ名と突き合わせればこの食い違いは保留として表に出る。

**候補が割れたら諦める。** `ComposerFinder` / `ConductorFinder` と同じ扱いで、推測で埋めない（`TAGGING_POLICY.md` 7章 原則4）。

#### 7.4.4 保留の種類

`TAGGING_POLICY.md` 3.5 規則2 の `HOLD_DATE_UNKNOWN` を含め、アルバム名では 3 つの保留が起きる。いずれも**条件が揃えば自動的に再判定できる**状態で、重大度とは別軸に持つ（`HoldReason`）。**保留は適用対象外**で、既定でもチェックされない（9.1）。

| コード | 条件 | 解ける条件 |
|---|---|---|
| `HOLD_WORK_UNKNOWN` | 作品エントリを同定できない（未登録・候補が割れた・作曲家が単位内で複数） | 作品エントリを足す／`composer` を直す／`albumOverrides` を書く |
| `HOLD_DATE_UNKNOWN` | `date` が未設定、または単位内で値が割れている（3.5 規則2） | `date` を埋める。**割れている場合は単位の切り方を先に疑う** |
| `HOLD_ARTIST_UNKNOWN` | `artist` が単位内で一意に決まらない | `artist` を直す（R-203 / R-402 と同じ母集団） |

`HOLD_ERA_UNKNOWN`（`TAGGING_POLICY.md` 7.5 の団体名）と同じ仕組みに乗せる。

**保留の根拠には、次にどの画面で何をするのかまで書く**（2026-08-15 追加）。保留の理由だけを書くと、利用者は手近な導線を試すしかない。`HOLD_ARTIST_UNKNOWN` は**個別例外では解けない**（`albumOverrides` に `artist` は無い）にもかかわらず、「このアルバムの扱いを決める」で対象外にすれば一覧からは消える。それはタグが割れたまま消えるだけで、規則2 の保留を規則6 で握り潰すことになる。

| コード | 根拠に書く操作 |
|---|---|
| `HOLD_WORK_UNKNOWN` | 作品エントリが無いなら「作品を辞書に追加」。作曲家が複数なら「このアルバムの扱いを決める」 |
| `HOLD_DATE_UNKNOWN` | 別々の録音ならフォルダを分ける。同じ録音なら明細をダブルクリックしてファイル一覧タブで `date` を揃える。主作品 + カップリングで録音年が違うだけなら「このアルバムの扱いを決める」で主作品の年を指定する（3.5 規則2・規則5） |
| `HOLD_ARTIST_UNKNOWN` | フォルダを分けるか、ファイル一覧タブで `artist` を揃える |

#### 7.4.5 個別例外（`albumOverrides`）

3.5 の規則2・規則4・規則6・規則7 は、いずれも「そのアルバムだけ」の例外を認めている。**規則そのものを一般化しない**ため、作品エントリではなくアルバム単位に紐づく別のリストに持つ。

| 項目 | 内容 |
|---|---|
| `folder` | ライブラリルートからの相対パス |
| `disc` | 対象のディスク番号。省略するとそのフォルダの全ディスク |
| `composer` | 単位の作曲家を明示する。主作品 + カップリング（3.5 規則5）で使う |
| `workName` | 作品名を明示する。版の違い（規則4）・同一演奏の別リリース（規則7）で使う |
| `date` | 単位の年を明示する。主作品 + カップリングで録音年が割れている場合に使う（規則2） |
| `exclude` | `true` ならアルバム名の対象外にする。本物のコンピレーション（規則6）で使う |
| `note` | 例外の理由。**必須の運用とする。** 理由の書いていない例外は後から消せない |

**`date` は割れているときだけ効く**（2026-08-15 追加）。タグの年が単位内で一意ならそちらを採る。一意な値まで上書きできると、タグを直したあとも辞書の古い指定が生き続け、その食い違いがどこにも出ない。**選ばせるのは単位内にある年だけ**とし、手入力させない（4 桁でない値は `DictionaryValidator` がエラーにする）。

2026-08-11 時点の該当は、規則5 が 4 単位・規則6 が 4 単位・規則7 が 1 組（3.5 補足2）。2026-08-12 に規則6 の対象を数え直して 18 フォルダになった（3.5 補足3）。

**`folder` は検査結果から埋める**（7.3.2）。手で相対パスを打たせない。打ち間違えても例外が黙って効かなくなるだけで、原因が画面から分からない。**比較は Unicode の正規化形（NFC）にそろえる。** 濁点付きの仮名は NFC と NFD のどちらでも保存でき、見た目が同じでも文字列としては一致しない（実ライブラリの `シェエラザード` が NFD だった）。

#### 7.4.6 初期投入

`tools/AlbumProbe` に雛形出力を足し、220 単位分の `works` 候補を JSON で吐かせる。**読み取りのみで、ライブラリには書き込まない。**

- 各単位の作曲家・現在の `album` 値・フォルダ名を集め、`composer` と `aliases` / `aliasesJa` を埋めた状態で出す。ラテン文字のものを `aliases`、日本語を含むものを `aliasesJa` に振り分ける
- `canonical` は空にする。**ここは人が埋める。** 現在の `album` 値は誤っていることがあり（3.5 補足2）、機械が正規形として採用してはならない
- 同じ作曲家で手がかりが重なる単位は 1 エントリにまとめる。ブルックナー 8 番の 9 単位が 9 エントリになると、重複の解消がそのまま作業量になる

**まとめる鍵はフォルダ名だけにする。`album` の値を鍵にしてはならない**（2026-08-11 の実測で確定）。

- `Brahms 交響曲全集` や `Shostakovich Symphony No.5,9` のように**複数の作品にまたがる値**が橋渡しになり、別作品が 1 エントリに融合する。実測ではブラームスの交響曲 1〜4 番が 1 件に、シューベルトの 8 番と 9 番が 1 件に潰れた
- フォルダ名は**作曲家フォルダを飛ばした先頭のセグメント**を採る。末端から採ると `ワーグナー\タンホイザー\第一幕` と `ワーグナー\ワルキューレ\第一幕` が `第一幕` で繋がり、別の歌劇が融合する。幕・ディスクは作品の下位区分であって作品ではない
- そのセグメントの「最初の `-` より前の部分」も鍵に足す。`ブルックナー 8 - Wand` から `ブルックナー 8` を拾わないと、同じ作品が演奏者の数だけ別エントリになる

`album` の値は**候補として拾い、次の 2 つを外してからエイリアスにする**。

1. **同じ作曲家の複数のエントリが名乗る値**（全集・カップリング盤、および誤ったタグ）。作品を特定できないのでエイリアスに使えない
2. **別の作曲家名を含む値**。判定は R-210 と同じものを使う。`シューベルト 8` のフォルダに付いた `Mendelssohn : Symphony No.4 "Italia"` のように、そもそも別の作品のタグであることがある。**一致しても誤りとは限らない**（ブルックナー 3 番の `Bruckner:Sym.No.3 "Wagner"` は愛称であって誤りではない）ため、落とすのではなく一覧に出して人が決める

**作曲家フォルダの直下にファイルがある単位は雛形に出ない。** 手がかりになるセグメントが無いためで、`グリーグ` `バッハ` `ビバルディ` が該当する。これらは雛形の「6.1 雛形にできなかった単位」に出るので、そこから手で足す。

埋めた雛形は `AlbumProbe --import-works` で辞書へ入れる。**JSON を手で継ぎ足さない。** 辞書の読み書きは本体と同じ `DictionaryLoader` / `DictionaryWriter` を通し、取り込み前に `DictionaryValidator` で止める。手で足すとキーの綴りが本体の書き方と食い違い、読めない辞書ができる（2026-08-12 に実際に起きた）。

**取り込みは冗長な別名を落とす**（`RedundantAliasCleaner`）。雛形のエイリアスはフォルダ名そのままなので、`canonical` に `Symphony No. 7` と書くと、雛形が集めた `Symphony No.7` が同じ正規化キーのまま残る。索引は先勝ちで後者を捨てるため引ける範囲は変わらないが、警告だけが作品の数だけ積み上がる（2026-08-14 に 41 件）。**落としたものは一覧で出す。** 黙って捨てると、雛形を書いた本人が「登録したのに一覧に無い」と迷う。

**同梱の既定辞書には入れない**（13章 D5）。作品エントリは所蔵に完全に依存するため、他の所蔵では無意味な値になる。同梱辞書には `works: []` と `albumOverrides: []` を空で置き、スキーマだけを示す。

## 8. バックアップと復元

### 8.1 方針

**音声ファイル本体は複製しない。** 対象ライブラリは30GBあり非現実的。タグのみをスナップショットする。

### 8.2 動作

適用の直前に自動でスナップショットを取る（ユーザーが明示的にバックアップを取っていなくても）。

保存先: 既定はライブラリ直下の `backup_{yyyyMMddHHmmss}\`。設定（`%APPDATA%\MusicTagAuditor\settings.json` の `backupRoot`）で任意のフォルダに変更できる。

- 保存先を変えても履歴からは消えない。バックアップ履歴は設定した保存先とライブラリ直下の**両方**を走査してマージする
- 保存先を複数ライブラリで共用しうるため、共用先のエントリは `manifest.json` の `libraryRoot` が一致するものだけを対象とする。フォルダ名が衝突する場合は `backup_{yyyyMMddHHmmss}_{連番}\` にする
- 設定を読めない場合は既定値へフォールバックして起動する。設定は入力し直せるが、起動できないと何もできない
- 設定ファイルには他の項目（5.4 の `lastLibraryRoot`）も入る。保存時は現在の設定を土台に該当項目だけを差し替える。全体を組み直すと、直前に設定したもう一方が黙って消える

- `tags_snapshot.json` — 全ファイルの全タグ（カバーアートを除く）
- `manifest.json` — 適用した差分の内容、日時、対象件数

### 8.3 復元

アプリ内の「バックアップ履歴」からスナップショットを選んで復元する。復元前に差分を表示し、何が戻るのかを確認できること。

スナップショットの JSON はアプリなしでも復元できる形式にしておく（外部スクリプトから読める素直な構造にする）。

**スキーマ版より前に取ったバックアップでは、そのとき記録していなかったフィールドを復元対象にしない。** 記録が無いことは「値が空だった」と区別できず、現在の値と突き合わせると必ず差分が立つ。復元項目は既定でチェック済みなので、そのまま適用すると今入っている値を消してしまう。`comment` は版 2 から記録しているため、版 1 のバックアップからは復元しない（同梱の `restore-tags.ps1` はスナップショットに実在するフィールドだけを回すので、構造的に同じ結果になる）。

## 9. 適用フロー

```
1. スキャン        ライブラリを走査し全タグを読み込む
      ↓
2. 検査            ルールを適用し、違反と修正案を生成する
      ↓
3. 選択            ルール単位・行単位でチェックを付ける
      ↓            （既定のチェック状態は下記）
4. バックアップ    自動でスナップショットを取る
      ↓
5. 適用            チェックされた差分のみ書き込む
      ↓
6. 検証            書き込んだ全項目を読み戻して照合する
      ↓
7. 結果表示        成功件数・失敗件数・不一致件数を表示する
```

**6 を省略しない。** 書き込みが成功したことと、意図した値が入っていることは別である。不一致が1件でもあれば警告を出し、詳細を表示する。

**工程 3 の選択は工程 5 の可否へ即座に反映する。** チェックを変えたら、その場で選択件数の表示と適用ボタンの活性が追従すること（5.3）。既定のチェック状態はあくまで出発点であり、そこから動かせない作りにはしない。

**工程 7 のあと、検査結果タブは全クリアしない。** 適用に成功した項目だけを検査結果から取り除き、未対象（チェックが外れていた項目）・失敗・不一致・競合はチェック状態を保ったまま残す。全クリアして毎回「検査」をやり直させると、直後の項目に対する再確認が積み上がって使いにくいため。ファイル一覧・フォルダツリーは、書き込んだタグの値を反映するため読み直す。

### 9.1 既定のチェック状態

**修正値が決まっているかどうかで決める。重大度だけでは決めない。**

| 条件 | 既定 | 判定区分 |
|---|---|---|
| ⛔ または ⚠ で、修正値が決まっている | チェック済み | 確定 |
| 修正値を決められない（重大度によらず） | 未チェック | 要確認 |
| ❓ | 未チェック | 要確認 |
| 保留（`HOLD_ERA_UNKNOWN` 等） | 未チェック・適用対象外 | 保留 |

⚠ を含めるのは、該当する R-102 / R-103 / R-104 がいずれも修正値を一意に決められるため。genre は必ず `Classic`、単一ディスクなら `1/1`、ISO 形式からは年を抽出できる。

**重大度が ⛔ でも、修正値を決められなければチェックしない。** R-203 は 162 件検出しても指揮者を特定できたのは 34 件だけで、残りは一覧に出すに留める（`TAGGING_POLICY.md` 7.4）。

## 10. データモデル（概略）

実装は `src/MusicTagAuditor.Core/Models/` 配下。以下は概略であり、フィールドの意味は実装のドキュメントコメントを正とする。

```csharp
sealed record TrackTags(
    string RelativePath,
    string FullPath,             // ファイルの絶対パス
    AudioFormat Format,          // M4a, Flac, Id3
    IReadOnlyDictionary<TagField, IReadOnlyList<string>> Fields,
        // フィールドごとの格納値。2 値以上あるのは AIMP が `;` で分割した状態で、
        // 検査ルールが検出する対象になる（TAGGING_POLICY.md 3.4）。1 値へ丸めずに保持する
    IReadOnlyDictionary<string, string[]> RawTags);   // 未知タグの保持用

// Title / Artist / Composer 等は Fields から GetSingle(TagField.X) で導出する
// 計算プロパティ（複数値は "; " で連結して 1 文字列にする）。HasMultipleValues(field) で
// 連結されたかどうかを判別できる

enum Severity { Error, Warning, Info, Manual }
    // Error/Warning/Info はルールの重大度（6章）。Manual は手編集（段階6）で入った値を表す
    // 独立区分で、原則違反の重さを持たない

enum HoldReason { None, EraUnknown, WorkUnknown, DateUnknown, ArtistUnknown }
    // 修正を保留する理由。重大度の3段階とは別軸（TAGGING_POLICY.md 7.5）。
    // EraUnknown は date が未設定で収録時点の団体名を決められない状態（HOLD_ERA_UNKNOWN）。
    // date が埋まれば自動的に再判定できる
    // WorkUnknown / DateUnknown / ArtistUnknown はアルバム名（R-504）の保留（7.4.4）。
    // いずれも条件が揃えば自動的に再判定できる点は EraUnknown と同じ

sealed record TagChange(
    string RelativePath,
    TagField Field,
    IReadOnlyList<string> BeforeValues,   // 現在の値
    IReadOnlyList<string> AfterValues,    // 修正後の値。修正案が無ければ現在の値と同じ
    string RuleId,
    string Rationale,            // 「フォルダ名から特定」等。UI に必ず出す
    Severity Severity,
    HoldReason HoldReason = HoldReason.None,
    bool ClearsValue = false);   // 値を消すことが目的の変更か。手編集だけが立てる
```

`IsSelected`（適用対象にするか）と `Classification`（確定/要確認/保留の判定区分）は `TagChange` の位置パラメータではなく、`Severity` / `HasFix` / `HoldReason` から導出する計算プロパティ。既定値は9.1節の表と同じ条件で決まる。

`RawTags` は必須。読み取ったが編集対象でないタグ（`iTunNORM`、`iTunSMPB`、CDDB ID 等）を保存時に失わないため。

**ID3v2 ではこれらが `COMM` フレームの description に入る。** そのため `comment` を ID3 の論理フィールドとして扱うと、読みでバイナリ相当の値を拾い、書きで音量正規化情報を巻き添えに消す。ID3 で `comment` を扱わないのはこの理由による（`TAGGING_POLICY.md` 4.4）。`RawTags` は記録用で復元には使わないので、一度消すと戻せない。

## 11. 非機能要件

| 項目 | 要件 |
|---|---|
| スキャン性能 | 1,000ファイルを10秒以内。UI をブロックしない（進捗表示とキャンセル） |
| 書き込み | 1件ごとに例外を捕捉し、1件の失敗で全体を止めない。失敗一覧を表示する |
| 文字コード | UTF-8 で読み書きする。Shift-JIS が誤解釈された既存タグを検出できること（R-403） |
| 対象拡張子 | `.m4a` `.flac` `.mp3` `.aif` `.aiff`。将来 `.wav` `.ogg` `.opus` を追加可能な構造にする。**形式によって扱えるフィールドが違う**（`comment` は ID3 で扱わない。`TAGGING_POLICY.md` 4.4） |
| ログ | 適用処理は全件ログに残す。事後の追跡に必要 |
| 除外 | `backup_*` フォルダはスキャン対象外 |

**スキャン性能の 10 秒 / 1,000 ファイルは、OS のファイルキャッシュが温まった状態で測る。** これは実装が無駄な I/O をしていないことの上限であり（全ファイルを読むと 3 倍以上かかる。`DEVELOPMENT.md`「タグ入出力の実装上の注意」）、初回走査の実時間ではない。冷えた状態の所要時間は保存先の媒体で決まり、実装では短縮できない（実測: HDD 上の 1,097 ファイルで 16.8 秒 ≒ 1 ファイル 1 シーク相当。2026-08-13）。**利用者が初回に体感する待ち時間は、同じ行の後段——進捗表示とキャンセル——で受け止める。**
