# 動作確認

`dotnet build` と `dotnet test` が通っても、XAML のリソース参照や DI の登録漏れは実行するまで
表に出ない。**View / XAML / テーマは単体テストの対象外**（[README.md](../README.md#テストとカバレッジレポート)）
なので、UI に触る変更をしたらアプリを起動して確かめる。

**実行は [verify-ui スキル](../.claude/skills/verify-ui/SKILL.md) を使う。** 手で
`MusicTagAuditor.App.exe` を叩かない。ここに書くのは、そのスキルがなぜその手順を踏むのかの根拠。
呼び出し方と引数はスキル側にある。

## 実ライブラリでは動かさない

**実ライブラリから数フォルダをコピーしたテスト用ライブラリを開く。** 実ライブラリを開いたまま
操作すると、押し間違い 1 回で所蔵のタグが書き換わる。コピーであれば「適用」まで含めて確かめられる。

- 置き場はリポジトリの外。音源をコミット候補に入れない
- 毎回作り直す。前回の適用結果が残っていると、何を検出したのかが読めなくなる
- **M4A と FLAC の両方を入れる。** 形式で通る経路が違う（[DEVELOPMENT.md](DEVELOPMENT.md#タグ入出力の実装上の注意)）
- 規模は小さくてよい。7 ファイル・128MB のコピーで検出 12 件・保留 4 件が出た

開かせ方は第 1 引数。`MainViewModel.StartAsync` が引数を前回のライブラリより優先する。

## 設定・辞書・ログは分離できない

`AppConst.GetAppDataDirectory` は `Environment.GetFolderPath` を使う。これはシェル API を見るため、
`APPDATA` / `LOCALAPPDATA` を差し替えても実際のパスが返る（実測で確認済み）。したがって次の 3 つは
利用者のものを共有する。

| 対象 | 場所 | 影響 |
|---|---|---|
| `settings.json` | `%APPDATA%\MusicTagAuditor` | バックアップ先・前回のライブラリ・折り畳み状態 |
| `dictionary.json` | 同上 | 下記のとおり、エージェントのシェルからは実体が見えない |
| ログ | `%LOCALAPPDATA%\MusicTagAuditor\logs` | 日次ローテーション。検証の行が利用者のログに混ざる |

**とくに `settings.json` は、テスト用ライブラリを開いた時点で書き換わる。**
`OpenAsync` が `RememberLibraryRoot` を呼び、`lastLibraryRoot` がテスト用ライブラリを指す
（[MainViewModel.cs:501](../src/MusicTagAuditor.App/ViewModels/MainViewModel.cs#L501)）。
戻さないと、次に利用者が起動したとき、消したはずのテスト用ライブラリを開きにいく。
だからスキルは起動前に退避し、失敗しても `finally` で必ず戻す。

バックアップ先も同じ設定に入っている。適用まで試すと、検証のバックアップが実運用の履歴に混ざる。

**ただし辞書だけは例外で、エージェントのシェルからは実体が見えない**（2026-08-22 に確認）。
シェルから見える `%APPDATA%\MusicTagAuditor` は古い写しであり、**そのシェルから起動した
アプリも同じ写しを読む。** 実体が個別例外 29 件のとき、検証で起動したアプリのログは 18 件と
出た。つまり**検証での辞書の書き換えは利用者の辞書に届かない**（届かないので、退避しようと
しても写しを退避するだけになる）。

**この非対称は毎回確かめてから使う。** `辞書を読み込んだ … 個別例外=N` の行を利用者の実際の
件数と突き合わせ、食い違っていることを確認する。一致していたら実体を触っているので、辞書を
書き換える検証はやらない。写しの側は汚れるので、足した項目は検証のあと**足した 1 件だけ**を
消す。全体を書き戻すと、写しと実体のどちらを壊すか読めない。

## 判定の拠りどころ

- **起動の成否はプロセスの生死で見る。** 起動時例外はログに残らずに落ちることがあるので、
  ログの有無では判定できない。起動行・辞書の構成・スキャン結果は当日分のログに出る
- **画面は `user32!PrintWindow` にフラグ 2（`PW_RENDERFULLCONTENT`）を渡して撮る。**
  背面のままでも撮れる。**画面全体のキャプチャは使わない。** 前面化は失敗することがあり、
  そのとき写るのは利用者が見ていた別のウィンドウになる。一度これで無関係なブラウザ画面を撮った
- **操作は `UIAutomationClient` で足りる。** タブの選択（`SelectionItemPattern`）、ボタンの押下
  （`InvokePattern`）、活性状態の取得までできる。実測ではタブ 6 個・ボタン 33 個が列挙でき、
  「検査」の押下から結果表示まで到達した
- **モーダルダイアログの探索だけは UI Automation では足りない。**
  `AutomationElement.RootElement.FindAll(Children)` に出てこないため、探しても見つからず
  「開いていない」と読み違える。実際に 2026-08-22 にこれで 5 回遠回りし、`InvokePattern` の
  失敗・クリック座標・コマンドの早期 return と、当たっていない原因を順に疑った。
  `EnumWindows` でプロセスの可視ウィンドウを列挙すれば最初から `visible=True` で出ている。
  HWND を `AutomationElement.FromHandle` に渡せば、あとは同じように操作できる
- **ダイアログの文言は UI Automation から読める。** `TextBlock` が Name として取れるので、
  注意書きの確認は画像より確実
- **一覧の行の中身も Name として読める。ただし振ってあるグリッドに限る。**
  `AutomationProperties.Name` を振ってあるのは検査結果タブの上段（`RuleResultGrid`）と
  下段（`InspectionChangeGrid`）、辞書に無い値（`UnknownValueGrid`）、ファイル一覧
  （`TrackGrid`）、保留中の編集（`ManualEditChangeGrid`）の 5 つ。**それ以外は型名が返る**
  （辞書タブとダイアログの表がまだ読めない）。書式と足し方は
  [DEVELOPMENT.md](DEVELOPMENT.md) の「一覧の行には名前を振る」
- **列挙できるのは画面に出ている行だけ。** DataGrid が仮想化しているため、スクロールの外は
  出てこない。読めた行数が画面の件数表示と食い違うのはこれが理由で、異常ではない
- **押すボタンは名前で特定する。** 索引で選ぶと、ボタンが 1 つ増えただけで別のものを押す

## ユーザーに委譲してよい範囲

ここまでは自分でやる。委譲してよいのは次の 3 つだけで、起動確認ごと丸投げしない。

- **スプリッタや列幅のドラッグ。** UI Automation に対応するパターンが無く、実座標の操作は
  利用者の画面を奪う
- **実ライブラリでしか出ない事象。** テスト用ライブラリに再現しない所蔵固有の問題
- **主観的な見え方の判断。** 配色や間の取り方が意図どおりか

依頼するときは、**自分で確認できたこと**と**確認できていないこと**を分けて書く。
